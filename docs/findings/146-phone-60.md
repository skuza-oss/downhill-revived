# 146: The throttled Mi 11i at 2x and 4x paced 60: where a race field goes, and what moved it

Status: current
Checked: 2026-11-04

2026-11-04, branch `perf/phone-60` (from main `8306254`, 0.7.9 + finding 145). The goal: hold 60 in
races on the rooted Mi 11i throttled to finding 127's frozen low-end profile, at render scale 4x
and 2x (paced 60, the player default). Not reached: the race's slow middle went from 37-39 to
48.5-49.6 fps at 2x and from 36.5-36.9 to 44.1-45.1 at 4x. What moved it, what limits it now and
what is left are below.

## Summary

- **2x had never been measured on this profile.** On main it runs like 4x in the middle of the
  race: 38.8 and 37.0 fps (4x: 36.5-36.9), CPU-bound (`limit=cpu:gs`, `cpu:vu`), the GPU at 5-6 ms
  a frame. 4x adds a GPU limit at the race start (14.8 ms) and in places later (16-21 ms).
- **Seven code changes, all output-preserving**, and two build options (line tables, PGO):

  | | what | deterministic window 3400-7000, 2x | race fields 3300-4300, 2x |
  |---|---|---:|---:|
  | main | | 53.84 fields/s | 42.15 |
  | 1-3 | GS decode in place, spin once per wait, strip vertices converted once | 57.36 / 57.41 | |
  | 4 | touch controls in the present pass | 58.77 | |
  | 5-6 | Z-probe readback copied at once; the conversion cache keeps two vertices | 59.76 | 47.71 / 47.58 |
  | 7 | PACKED strips decoded and drawn in batches | 60.45 | 49.57 / 48.69 |
  | + PGO | `build_apk.py --pgo-use` with a profile of one race | 68.60 | **55.28 / 55.19** |

  At 4x, fields 3300-4300: main 42.09, the final PGO build 50.06 fields/s (+19 %; the GPU limits
  more there). In the slow stretch at 2x (fields 3300-4300) the per-field CPU went: game 21.9 -> 15.0 ms, VU 18.5 ->
  14.4, GS 18.4 -> 13.7, render 14.5 -> 12.2; the process 77.3 -> 57.8 ms a field.
- **Player config** (paced 60, delta-time clock, the brief's bench window 3400-5800; the game's
  30 s perf lines):

  | | race start | middle | bench window |
  |---|---|---|---:|
  | main 2x | 51.0 / 51.2 | **38.8 / 37.0** | 53.7 / 54.2 |
  | branch 2x, PGO | 53.7 / 53.8 | **49.6 / 48.5** | 55.8 / 56.0 |
  | main 4x | 50.5 / 50.6 (gpu) | **36.5 / 36.9** | 46.3 / 37.8 / 43.1 |
  | branch 4x, PGO | 52.2 / 52.2 (gpu) | **44.1 / 45.1** | 51.9 / 50.2 |

  (Main 4x is the brief's two runs and one of this round's.) These runs scatter: the delta-time
  clock steps by wall time, so riders end up in different places and the same 30 s of race costs
  differently (the middle of one unchanged build measured 40.7 and 45.7). The deterministic runs
  above are the comparison; each change was measured that way.
- **The game is unchanged.** Windows state trace boot (600) and race (5000) against main: all rows
  match. The phone's own state trace of the final APK (all changes and PGO) against main's APK on
  the phone: all 13 columns identical over 5000 race fields. Every native frame's vertices, indices,
  commands and box hashed the same as main's for all 4,999 frames of a deterministic Windows race.
  Details under "Checks".
- **What limits it now:** in the slow middle the VU thread (busy 17-18 ms of a 20-21 ms frame) and
  the game thread, then the GS thread; the six cores are about 3.2 busy. At 4x the GPU as well (15-17
  ms). Holding 60 there needs about another 20 % off the VU, EE and GS threads.

## Method

- Profile: `phone_throttle.py --apply t612 --big-max 1209600 --little-max 1497600` (finding 127),
  `--restore` at the end. Release-signed APKs installed with `adb install -r`.
- A runner in the scratch folder (not committed), adapted from the brief's: it writes `DHD_*` keys into
  the app's dhd.ini via root, force-stops third-party apps, cools 60-90 s with the screen on, starts
  the app, samples clocks every ~3 s, optionally runs `simpleperf record -p PID` for a given span,
  pulls dhd.log and puts the original dhd.ini back.
- **Deterministic runs** (`DHD_FRAME_CLOCK=1`, otherwise the player config): every run draws the
  same frames, unpaced (`pacing=unpaced`, V-Sync mailbox), so fields/s over a fixed field window is
  throughput on identical work. Two runs of one build: 57.355 and 57.406 (0.1 %); three of another
  in the slow window: 47.71, 47.58, 47.58. The player-config runs (delta-time clock) differ by up to
  10 % between runs of one build (see above), so they gave the before/after picture, not the
  per-change gains.
- **The slow stretch**: the race's middle 30 s are fields ~3100-4300 (the perf lines' fields in a
  deterministic run). Window 3300-4300 measures just that.
- Clocks stayed at the caps in every in-window sample (1.497 / 1.209 GHz, GPU 315 MHz); the A78
  read 0.96 GHz in one sample of one run.
- Profiles: simpleperf at 1 kHz (and frame-pointer call graphs at 500 Hz), symbolised with the
  build's `libmain.debug.so`. `build_apk.py --line-tables` (new) gives that file line tables
  (build_host64's `--debug`, code unchanged), so samples map to source lines.

## Where a slow field went (main, 2x, the race's middle)

simpleperf, 35 s, 116,753 samples: game 27.8 %, gs 24.0 %, vu 23.9 %, render ("native") 20.5 %.

| thread | on the A78s | top |
|---|---:|---|
| game | 76 % | `idle_wait` 25 % (spinning), `rc_func_0021B8A8` 6.0, the SPU2 mixer `render` 5.9, `rc_func_00213C08` 4.1, VU0 (`run_fast_program`, `ps2_vu0_run`, `native0_transform`) 8.4 |
| vu | 62 % | `native_geometry_loop` 22, `native_clip_run` 12, `unpack_stream` 7.8, `vif_feed` 5.4, `ps2_vu1_run` 4.9 |
| gs | 23 % | `gs_feed` 48, `native_draw` 37, `load_clut` 4.3, `gs_palette` 2.8 |
| render | 16 % | kernel `rb_next` 11.4 + `kgsl_iommu_get_gpuaddr` 4.4 (see below), `memcpy` 5.2, `dhdr_native_zread_take` 3.1, wgpu |

- **The game thread spun a quarter of its samples** on a big core while the GS thread ran three
  quarters of its time on the A55s. `idle_wait` spun `DHD_SPIN_US` (3 ms on Android) again after
  every wake, and the GS thread wakes a waiting EE at every packet it retires (change 2).
- **The GS thread did ~300 ns of work per strip triangle**, ~50,500 of them a field (a field's
  draws: 50,548 strip triangles, 968 sprites, 54 fans, all but 29 from VU1). The time was spread
  over per-qword dispatch, `vertex_kick`'s copies, a float divide per vertex coordinate, three
  conversions of each strip vertex, an indirect call and per-draw state checks (changes 1, 3, 6, 7).
- **About 17 % of the render thread was the Adreno driver allocating GPU memory.** A frame-pointer
  call graph puts `rb_next` and `kgsl_iommu_get_gpuaddr` under `kgsl_ioctl_gpuobj_alloc`, called
  from `vkBeginCommandBuffer` and command recording. The driver gives a command buffer's memory back
  at `vkResetCommandPool` (`gpuobj_free`) and takes it again at the next begin; the kernel finds a
  free GPU address by walking the process's allocations. Pool flags do not change this (below), so
  the lever is fewer command buffers a frame (change 4).

## Changes

Each in port/; src/ untouched. Numbers are the deterministic 2x runs unless noted.

1. **`4fb0c33` GS: PACKED qwords decoded in place.** `gs_feed` runs whole PACKED qwords from the
   packet with the tag's counters in locals, and `packed()` stores RGBAQ/ST/UV/XYZ directly (one
   switch a qword, not two through `vertex_write`). Player config: the middle 37.0-38.8 -> 41.4 fps
   with only the in-place decode; GS CPU 20.1 -> 19.0 ms.
2. **`00d5fe6` Graphics queue: a wait spins `DHD_SPIN_US` once.** A call within 50 us of the last
   return goes on with that wait's spin. The game thread's `idle_wait` share fell from 25 % to 10 %
   of its samples; middle 41.4 -> 42.2 fps (player config). With the fix, `DHD_SPIN_US=0` and 300
   measure the same as the default (57.26 / 57.41 full window; 47.53 / 47.40 / 47.58 slow window).
3. **`d48789b` Native: a strip's shared vertices are converted once.** `native_record` multiplies
   by 0.0625f instead of dividing by 16.0f (the same value) and takes a strip's or fan's two shared
   vertices from the last triangle's conversion when their register bytes, offset, FST and state
   are the same. Changes 1-3 together: 53.84 -> 57.36 / 57.41 fields/s (+6.6 %); game 16.7 -> 14.9,
   GS 13.8 -> 12.0, VU 14.3 -> 13.4 ms.
4. **`615ccb5` Native: the touch controls drawn in the present pass.** The overlay had its own
   command buffer, two buffer writes, a submission and a render pass that loaded and stored the
   whole frame after every present. C now hands the shapes over before `dhdr_native_present`, which
   draws them as its pass's last draws (the same pipeline over the same picture), and
   `dhdr_surface_present` skips them for that picture; buffers are written only on a change.
   57.38 -> 58.77 (+2.4 %), render thread 12.68 -> 11.16 ms.
5. **`dcf09c9` Native: the Z probe's readback copied at once.** `zread_take` built each word from
   four byte loads of the mapped buffer (~0.4 ms a picture, 3.3 % of the render thread); one copy,
   then each word from little-endian.
6. **`606be3a` Native: the conversion cache keeps the two shared vertices only.** Saving three
   vertices and their pixels was 5 % of the GS thread. 5 and 6: 58.77 -> 59.76 (+1.7 %).
7. **`1415e21` GS: PACKED triangle strips decoded and drawn in batches.** A PACKED tag whose loops
   are RGBAQ/ST/UV then one XYZ, with PRIM a strip, is decoded whole; each vertex is kicked as
   `vertex_kick` would (counters, ADC skips, parity, the last vertices) and the triangles go to a new
   `draw_strip` hook in batches of up to 256. The native renderer draws the first through
   `native_draw` and records the rest with each vertex converted once (`native_exact` per triangle
   when the exact probe is on; the field trace, interpolation and a skipped state go through
   `native_draw`). Slow window 47.62 -> 49.13 (+3 %; full window 59.76 -> 60.45), GS 15.6 -> 14.8
   ms. Strips are short, so the first triangle of each still costs a full `native_draw`.

Build options: `e57f991` `--line-tables` (above), and **`010ef97` `--pgo-generate` / `--pgo-use`**,
passed through to build_host64 (which has had them since finding 091). One instrumented race at 2x
(player config, fields to 7000) gave a 21 MB profraw; merged with the NDK's llvm-profdata and built
with it, the slow window went from 49.1 to 55.28 / 55.19 (+12.4 %; full window 60.45 -> 68.60):
game 17.0 -> 15.0, VU 16.1 -> 14.4, GS 14.8 -> 13.7 ms. Finding 091 had measured +2.5 % on an older
build. Not the default: the profile must come from the same core build, and this one comes from the
race it was measured on (other tracks and menus were not profiled or measured). As a release step
it needs an instrumented run per core build.

## What limits it now, and what is left

The final build (PGO), slow middle, player config: game 15.6-16.1 CPU / 13.8-14.1 busy, VU
15.7-15.9 / 17.1-17.3, GS 13.6-13.7 / 14.0, render 12.0 / 9.9 + 3.4-3.8 in the present, on a 20-21 ms
frame. The VU thread is the closest to the frame time; game and GS follow. Default scheduling is
best: two big cores serve four busy threads, and a thread moved to the A55s takes 1.5-2.5 times as
long.

1. **VU1 (14.4 ms a field in the slow window):** `native_geometry_loop` 22 %, `native_clip_run` 12 %,
   VIF unpack and feed ~13 %, the interpreter and AOT blocks for the other programs ~15 %. The
   geometry loop is latency-bound (cheaper clamps gained nothing). What is left: drop the operand
   clamps where an operand is provably a previous result (every FMAC result is finite under
   round-toward-zero), which needs a per-operand proof in the native programs; or overlap two
   vertices per iteration.
2. **The EE (15.0 ms):** the recompiled game (`0021B8A8` 7 %, `00213C08` 5 %), VU0 macro code ~10 %,
   the SPU2 mixer ~8 % (`render`, `snd_adsr_tick`, `reverb_sample`), `w2c_core_address` 2.5 %. In
   the wasm2c core, so a core rebuild and the state trace with sound for the mixer.
3. **GS (13.7 ms):** now mostly the essential per-vertex work. `load_clut` and `gs_palette` are ~10 %:
   the texture key mixes 256 converted palette entries at each state change (a key over the raw
   CLUT entries, CPSM, CSA and TEXA would do; texture packs use their own hash), and the CLUT is
   reloaded from GS memory at every TEX0 write.
4. **Render thread (12 ms):** the Adreno driver's command-buffer memory churn (~15 %): fewer
   command buffers a frame (picture, Z probe and present are three; `DHD_ZREAD_FOLD` makes two).
5. **4x GPU (15-17 ms, up to 21):** the draw passes, the blended terrain's shading (finding 131).
   Pass count does not matter (8 against 18 passes cost the same). Not addressed here.
6. **PGO as a release step** is the largest single gain measured (+12.4 %); a profile from several
   tracks and the menus would cover more than this one race.
