# 259: the Redmi 9 on 0.8.6: Native VU crashes the Mali driver; speed, limits, stutter, picture

Status: current

Branch `perf/redmi9-259` from `main` ca519dde (release 0.8.6), started 2026-11-15. A measuring
lane: no code change. This file is the lane's plan while it runs and its finding when it merges.

## Goal and acceptance

The Redmi 9 (Helio G80: two Cortex-A75 at 2.0 GHz and six A55 at 1.8 GHz; Mali-G52 MC2, driver
r26p0; Android 11; not rooted) is the phone the 60 fps at 2x target is set on (finding 174). The
speed lanes since 0.7.15 (findings 195, 247, 249, 253, 256) were measured on a throttled stand-in.
This lane measures 0.8.6 on the phone itself, finding 156's route, at 1x and 2x:

1. the speed (whole race, race start, mid-race, p50 and p99, frames over 50 ms) beside the older
   Redmi 9 numbers, and Native VU off against on at 2x;
2. what limits it: the per-thread table of lane 257 (the frame budget on the throttled stand-in,
   merged into `main` after 0.8.6), and whether one thread, the CPU total on the
   two fast cores, or the GPU is the limit;
3. which leftover would pay here, with a size;
4. stutter: the first start against the second (the pipeline list of finding 256);
5. the picture with Native VU on.

Acceptance: the numbers below, each marked measured or guess; `check.py docs`.

Out of scope: changing code.

## Verdict

**0.8.6 with its default settings does not run on this phone.** Native VU (on by default since
finding 198) crashes the Mali-G52 r26p0 driver's shader compiler at the title screen, at every
start. With Native VU off the game runs, and that is what every number below is.

With Native VU off, 0.8.6 at 2x races at **48.6 fields/s** with every effect on: 11.4 short of 60
(a field takes 20.6 ms, 16.7 are allowed). The GPU limits there. With the three Performance
settings off (shadows, lens flare, particles) it races at **61.1 at 2x** and 66.1 at 1x.

The one change most worth a lane: **make Native VU run on this driver, or turn it off there by
itself** (a start that died in a mesh pipeline is already written down by the startup log; the next
start reads it and builds the same pipeline again). No speed leftover comes before that, and none
of them reaches 60 at 2x with the effects on.

## How it was measured

- **The build**: ca519dde as a debuggable APK, the release's native code
  (`build_host64.py --target android-arm64 --release --debug --pgo-use` with the release's profile
  `dhd-197.profdata`, then `build_apk.py`; the core module is the release's, sha256 5c038643...),
  installed with `adb install -r` over the debuggable 0.7.15 the phone carried (same debug key).
  Nothing uninstalled, no data cleared.
- **A run**: lane 198's recipe. The run's keys go into the app's dhd.ini through `run-as` and the
  file found there is put back after every run (md5 checked each time). Finding 156's route,
  `DHD_FPS=240 DHD_VSYNC=0 DHD_FRAME_CLOCK=1 DHD_RENDER=native DHD_WIDESCREEN=0 DHD_ASPECT=4:3
  DHD_SKIP_MOVIES=1 DHD_MEMCARD=0 DHD_SND_OFF=1 DHD_BENCH=300-14000 DHD_BENCH_EXIT=1`,
  `DHD_TIMELINE`, the screen on, 120 s between runs with the app closed. Battery 33.4 to 34.7 C
  at the runs' starts, up to 35.7 C at their ends.
- **Scenes** (fields): the race 6321-14000, its start 6400-7300, mid-race 9000-14000, the route
  300-14000. Columns as lane 257's: work = a thread's CPU minus its measured spin; busy = the field
  minus the thread's measured waits. This driver has no timestamp queries (finding 174): no GPU
  span.
- **No screen mirror in any kept run.** The first ten full runs were made while a screen mirror
  (a scrcpy server on the phone, about 6 % of a core plus the video encoder) was open, and five of
  them also under a script that asked the phone for a file every two seconds. All ten are void
  and none of their numbers is here; eight were run again (the profiler run and a second control
  run were not) and three runs were added. The mirror cost
  7 % of the race at 2x and 13 % at 1x (the void 45.1 and 52.7 against the clean 48.6 and 60.9).
  The picture is checked with `adb exec-out screencap` in two short runs of their own.
- **simpleperf was not run**: without root it needs the system property `security.perf_harden` set
  to 0, and this lane changes no system setting. So there is no split inside a thread.

## Native VU on: the driver's shader compiler crashes

Seven starts of seven with `DHD_NATIVE_VU1=on` (the players' default) ended 4.6 s after the start,
at the title screen, with

    crash: SIGSEGV at 0000000000000000 in thread dhd-pipelines
    #11 libGLES_mali.so cmpbe_v2_compile_multiple_shaders
    #15 wgpu_hal::vulkan::Device::create_render_pipeline
    #20 dhd_render::native::pipelines::build
    gs startup: watchdog: ... died at native pipeline E0180033E26BC000

| start | result |
|---|---|
| 2x, defaults (twice) | crash, thread `dhd-pipelines`, pipeline `E0180033E26BC000` |
| 2x, `DHD_NATIVE_SPEC=sync` (pipelines built on the render thread) | crash, thread `native`, the same pipeline |
| 2x, `DHD_NATIVE_SPEC=0` (the generic shader only) | crash, thread `native`, the same pipeline |
| 1x (twice, one with the pipeline list of an earlier run) | crash, thread `native` |
| 2x and 1x, `DHD_NATIVE_VU1=off` | runs (every start since, 24 of 24) |

- The pipeline is the first mesh pipeline a start builds: its key has the `MESH` and
  `MESH_TWO_SIDED` bits (`native_mesh_vertex` with a GS draw's fragment stage). The pipelines
  before it (`3C044`, `101C98B`, `1D20000`, none a mesh) build.
- It is not two compiles at once (it dies alone on the render thread too) and not a specialised
  stage (the generic one dies too).
- 0.7.16 ran Native VU on this phone (finding 198). `native.wgsl`'s mesh stages changed since then
  only in finding 249's two commits (`48962741`: a mesh's pixels run the GS draws' fragment stages;
  `6d9c4423`: a mesh's vertices arrive in clip space with their colour). Which construct the driver
  dies on was not looked for (guess: the pair of `native_mesh_vertex` with the no-perspective
  `Varyings`, the one thing every dying pipeline shares and no building one has).
- The next start logs `previous run: startup: died at native picture ...; died at native pipeline
  E0180033E26BC000` and builds the same pipeline again. Nothing turns Native VU off.
- Only the debuggable build ran here. The release APK has the same Rust library and shaders, so it
  is expected to do the same on this driver (not run: a release-signed APK cannot go over the
  debug-signed one without an uninstall).
- The first crashed start left the game's process alive (the runner's 25 minute timeout ended it);
  the others ended by themselves.

## What limits it (0.8.6, Native VU off; ms a field, means of two runs)

| | 2x race | 2x race start | 1x race | 2x race, effects off |
|---|---|---|---|---|
| field (fields a second) | **20.57 (48.6)** | 25.04 (39.9) | **16.44 (60.9)** | 16.37 (61.1) |
| game thread: work / busy / waiting for the GS | 14.07 / 13.84 / 6.73 | 16.65 / 15.08 / 9.96 | 12.61 / 12.56 / 3.88 | 13.15 / 13.13 / 3.24 |
| VU thread: work / busy / idle | 14.22 / 14.19 / 6.37 | 15.94 / 15.90 / 9.15 | 12.43 / 12.34 / 4.10 | 11.79 / 11.66 / 4.71 |
| GS front end: work / busy | 10.12 / 20.57 | 12.30 / 25.03 | 9.28 / 16.43 | 8.20 / 16.35 |
| render thread: CPU / busy / waiting for a field | 17.39 / 14.88 / 0.00 | 18.58 / 16.33 / 0.00 | 15.64 / 12.94 / 0.00 | 15.23 / 12.17 / 0.00 |
| render thread: waiting in the present | **5.68** | 8.71 | 3.49 | 4.21 |
| GPU span | no timestamps on this driver | | | |

The whole process uses 56.3 ms of CPU a 18.7 ms field over the route at 2x: 3.0 busy cores of
eight (1x: 3.3). The game's own placement (finding 149) keeps the render and GS threads on the six
A55; the game and VU threads share the two A75 and are on one in about half of the samples each.

Three more runs moved the threads (`DHD_AFFINITY`), one run each:

| run | race, fields/s | render CPU / busy | present wait | VU busy | game busy |
|---|---|---|---|---|---|
| 2x, the game's placement | 48.6 | 17.39 / 14.88 | 5.68 | 14.19 | 13.84 |
| 2x, no placement (`DHD_AFFINITY=0`) | 48.4 | 13.04 / 11.30 | **9.38** | 15.66 | 14.17 |
| 2x, render and game on the A75, VU and GS on the A55 | 31.9 | 9.39 / 7.80 | 3.31 | **31.28** | 13.54 |
| 1x, the game's placement | 60.9 | 15.64 / 12.94 | 3.49 | 12.34 | 12.56 |
| 1x, no placement | 62.9 (p99 31.7 ms against 23.6) | 13.04 / 10.84 | 5.00 | 14.24 | 13.45 |

- **At 2x the GPU limits** (measured, three ways). The render thread never waits for a field, and
  the time it does not work it waits in the present. With no placement it works 3.6 ms less a field
  and waits 3.7 ms more: the field stays 20.6 ms. Taking the pixels away shortens the field to the
  same 16.4 ms either way: the effects off at 2x, or 1x.
- **At 1x (and at 2x with the effects off) the render thread on a slow core limits**: busy 12.9 ms
  plus 3.5 ms in the present is the whole 16.4 ms field, and about 3.3 ms is the present's floor
  here (what is left of it when the render thread has 20 ms to spare). The game and VU threads
  wait about 4 ms each.
- **Is it one thread or the CPU total on the two fast cores? The total.** No thread is ready and
  not running: busy equals work for the game and VU threads (13.84 against 14.07, 14.19 against
  14.22). But the render thread's work costs 1.85 times as much on an A55 as on an A75 (17.39
  against 9.39 ms), the VU thread's 2.2 times (31.28 against 14.22), and three threads need a fast
  core: at 1x the game 12.6, the VU 12.4 and the render thread about 8.4 ms of A75 time are 33.4 ms
  a 16.4 ms field, two cores full. Whichever thread is put on the slow cores becomes the limit. So
  on the CPU side every thread's time counts here, the VU thread's included, as lane 257 asked.
- Race start at 2x: the GPU too (present wait 8.7 ms; with the effects off 60.9).

## Decisions

- **Every number is with Native VU off**: on does not start. The brief asked for on.
- **The first start is measured with `DHD_PIPELINE_LIST=0`**, not with a fresh install: the app's
  data is never cleared, and the switch builds at first use as a start without a list does.
- **The old build's numbers are read again from lane 198's timelines** over this lane's scenes, so
  both sides of the table use the same fields.

## Surprises

- **The default setting crashes on the target phone** and no lane since 0.7.16 ran this phone, so
  two releases' worth of Native VU work (findings 249, 253) never met this driver.
- **A screen mirror costs 7 to 13 % here.** It takes a slow core's time and the render thread
  lives on the slow cores. Every timing on this phone must be made with none open.
- **Pinning matters less than expected**: no placement at all equals the game's at 2x and is 3 %
  better at 1x (one run, with a worse p99). The placement of finding 149 was chosen on a stand-in
  whose render thread did not limit.
- The phone's dhd.ini is still the 46 bytes of a `cat` error an earlier lane left (finding 198);
  it was put back as found (md5 29bc64ce...). The app has no saves.
