# 267: the game runs on the iPhone XR (A12, 3 GB): the CPU floor and the guest memory's second base

Status: current

## Goal and acceptance

A player's iPhone XR (A12, iOS 18.7, 2.8 GB) runs 0.8.9 (finding 258's fix) and still fails, two
ways, in one dhd.log:

- three starts of four end with `host64 memory: reserve guest memory (12: Cannot allocate memory)`,
  the start's reservation included; the failure lists the free ranges: 1152 MiB at
  0x123654000-0x16b720000, 248 MiB at 0x170754000-0x180000000, 384 MiB at
  0x340000000-0x358000000 (and 25 MiB lower). Finding 258's one base needs 928 MiB free at the
  base and 33 MiB free 1792 MiB above it: no base fits there;
- the one start that reserved (base 0x104400000, its high part ending exactly at 0x180000000) died
  at the first VU0 call: `crash: SIGILL` in `w2c_core_ps2_vu0_run`, at `eor3.16b v5, v3, v1, v0`.
  EOR3 is the SHA3 extension (A13 and later); the iOS build used `-mcpu=apple-m1`.

Done means: the iOS builds select code for the A12 (docs/PLAYING.md's minimum), and a check in
the IPA audit refuses any instruction above it, proven on 0.8.9's binary (refused) and the new one
(passes); the guest memory reserves in every address space shaped like the player's log, one code
path; the failure's log lines stay. Proof without the phone: unit tests (`guest-place`,
`guest-access`), `test_guest_space.py` on the Mac with the player's address space rebuilt, the
same test inside the iOS Simulator, the Simulator app to a race, PC state traces equal 0.8.9's
(the PC build's code is not changed). Out of scope: the extended-virtual-addressing entitlement
(finding 258).

## Decisions

- **The CPU floor is the A12 for the Simulator too**: it runs what the phones run. The Mac keeps
  `apple-m1`. Floating point does not change: the core is built with `-ffp-model=strict
  -ffp-contract=off`, so `-mcpu` selects instructions only (EOR3, DOT, FRINT32 and the like are
  integer or exact operations with the same results); and the PC build is not touched.
- **What the check refuses** (`cpu_floor.py`'s docstring): every user-mode instruction of the
  features LLVM's apple-a13 and apple-a14 (= M1) add to apple-a12 (SHA3, SHA512, FP16FML, DotProd,
  FlagM, FlagM2, FRInt3264, RCPC-immo, SB), the M2's BF16 and I8MM, and SM3/SM4: the ones a compiler
  may pick by itself once the `-mcpu` allows it. Taken from `AArch64Processors.td`; each mask
  checked against clang's assembler. SHA512 (and SM3/SM4) only ever come from intrinsics or
  assembly that asks for them: in this app the network library's crypto (ring's CRYPTOGAMS
  assembly, the sha2 crate), which asks the CPU first (`hw.optional.armv8_2_sha512`). They are
  reported, not refused, or every build would fail. Words inside 16 or more bytes of printable
  text are skipped: ring's assembly keeps its credit string in the code section, and " CRY" reads
  as an LDAPURH. Not seen by any scan: LSE2 (no instruction of its own; the `-mcpu` is the cure).
- **iPads with an A10 (7th generation, iPadOS 17/18) stay below the floor**, as docs/PLAYING.md
  already says (A12 or later); this lane does not lower it.
- **Two host addresses, not a smaller low part or a fold.** The low part's 928 MiB are the PS2's
  own addresses (RAM views and mirrors up to 0x3a000000) that the core reaches with plain
  arithmetic; folding the high part next to it (258's "next step") would need one contiguous
  961 MiB to 1.2 GiB range, a compare and subtract on every dynamic access and a constant offset in
  every module data access. Two independent parts need only 928 MiB in one range and 33 MiB
  anywhere: the player's late address space has 1152 + 248 + 384 MiB.
- **The guest's addresses do not change**, only where the high part sits on the host: the window
  mask, the wild-access guard (`host64_outside`, `host64_memory_wild`) and every test of 258 stay.
- **Where the second base costs**: the call-site split's hot arm takes its part's base
  (`HOST64_SITE_BASE`). A module-data offset is the high part at compile time; any other site
  tests bit 30 of its base value (plain windows below the gap end at 0x36000000, window 56 is the
  high part's): `tst` + `csel` once per base value, shared by every access through it. The high
  base is read once per function into a local, as wasm2c reads the memory base
  (`HOST64_HIGH_LOCAL`). Measured as static instructions of `core_5.c` (wasm2c part 5 of 8 of
  0.8.9's core, the iOS flags, `-mcpu=apple-a12`, NDK clang 19): 355,693 before, 374,972 after
  (+5.4 %: about 9,700 `tst`/`csel` pairs and one load per function). No timing claim (no
  timing runs in this lane). The high base must be a pointer: from an integer (`(uint8_t
  *)uintptr`), LLVM stopped sharing the large module-data offsets between accesses and the same
  unit grew 13 %.
- **One code path**: the switch is `HOST64_TWO_PARTS`, as in 258; on one reservation the macros fold
  to the one base and the generated C differs only in an unused local.

## Surprises

- 0.8.9's program also carries SHA512 instructions (288) in two places: the sha2 crate and ring's
  assembly; both run-time checked, so not a crash.
- "The start" is the first constructor of the app's own image: dyld has mapped the program, its
  libraries and the shared cache, and malloc has its first regions. On the player's phone the
  start's reservation failed on three of four starts, so the start is not early enough for one
  base; nothing earlier is ours.

## Result

- **Cause 1, the CPU**: the iOS builds use `-mcpu=apple-a12` (the Simulator too; the Mac keeps
  `apple-m1`), and the IPA audit refuses any instruction the A12 lacks (`port/ios/cpu_floor.py`).
  0.8.9's program: refused (179 EOR3); this branch's: passes.
- **Cause 2, the memory**: the guest's two parts are reserved where each fits, the high part at
  a host address of its own; the guest's addresses, the access guard and the failure's log lines
  stay. The player's address space, rebuilt on a Mac and inside the Simulator: 0.8.9's one base
  fits nowhere, the two parts start.
- **Unproven**: a real A12 / 3 GB device. The next dhd.log from the player decides: the line
  `host64 memory: guest memory at 0x..., reserved ...: [0, 0x3a000000) there and [0x70000000,
  0x...) at 0x..., room to grow to N MiB`, then the title. Also unproven: the cost of the second
  base in time (static: +5.4 % instructions in one core unit); a Simulator state trace (the PC's
  traces are equal; the PC's code is unchanged).
