## 2. One centred menu layer

`port/hle/menu_page.c` (the game's SharedMenu popups run by the popup manager, finding 050) is the
layer. Its pages are now laid out as the game's centred popups (the pause menu, `func_0015E238`)
instead of the shell's right-aligned lists: title at (half, 0x40), rows from y 0x54 every 10 lines
centred on the view's middle (`X_LEFT_ALIGNED` 0), footer at (half, 0xCC). Font, colours, highlight
bar and panel are the game's own (the menu draws them).

New row kinds, so every page builds the same way:
- `menu_page_row` (button), `menu_page_text` (a dimmed line, not selectable);
- `menu_page_value(label, value, arrows)`: "Label:  < Value >", the arrows only when it can be
  changed; a pending value keeps its " *" outside the arrows; `menu_page_value_set` rewrites it.

Moved onto it: PC SETTINGS (all value rows), the exit menu, ONLINE (home, the public list, name and
code entry) and the RACE ROOM (Track and Computer Riders are value rows, code and players are text
rows). The original shell menus (main menu, OPTIONS, rider carousel, track map) are the game's and
stay as they are, right-aligned at x 530.

## 3. Mouse (and touch later)

Plumbing, one host API for every platform: `host_service_mouse_state(HostMouse *)` (host_api.h):
x, y in 65536ths of the picture (so window size, DHD_SCALE, letterbox and pillarbox bars don't
matter), buttons held, seen, and counters that only grow (moves, presses of left/right/middle,
wheel steps), so a click between two fields is never lost.
- x64 (`port/gs/present.c`): SDL3 mouse events from the SDL thread (`sdl_host.c` dispatch).
  The renderer reports where it last drew the picture in the window (`gs_picture_rect`, from
  `native_present_rect`'s cut rectangle), and the pointer is placed relative to it; high-DPI
  windows go through `SDL_GetWindowPixelDensity`. Touch arrives as SDL's mouse events.
- Browser (`port/web/www/main.js`, `worker.js`): pointer events on the canvas (mouse, pen,
  touch), placed in the contained picture of the canvas; a 64-byte block after the pads in the
  input SharedArrayBuffer; the worker answers `host_service_mouse_state` from it. The headless
  runner returns zeros.
- Android touch later: feed the same HostMouse (touch = left button, position as fraction).

In the core (`menu_page.c`, `menu_mouse_field` once a field from `pad_vsync`): while one of the
popup manager's menus is open (ours, and the game's own popups that it runs) and nobody is riding (`D_0029E290`):
- moving over an enabled row moves the menu's cursor there (hover selects);
- left click on a row = X; on one of our value rows, its "<" = Left, the rest = Right;
- right click = Triangle (back), anywhere;
- wheel = Up/Down, or Right/Left on a value row (it changes the value).
Hit-testing measures the rows with the menu's own font metrics (`func_0020F860` with the row
style's sizes) and the panel's margin; the widescreen 2D stretch (`port_fov_x`) is inverted.
Presses go into player 1's pad like a controller's (held 3 fields, released 3, a queue of 8:
`menu_mouse_merge` in `pads_read` and `pad_refresh`), so the menus play their own sounds and do
their own checks. Keyboard and pads are untouched; without mouse use nothing changes.

Cursor: the OS cursor shows when the mouse moves, hides after 3 idle seconds and while riding
(present.c `gs_cursor_tick`; main.js `cursor()` with the worker's riding flag).

Original shell menus: not bridged yet. Plan: the shell's menus are struct lists whose cursor is
`.x10` (main menu `D_004C6CA8`, OPTIONS `D_004C6D98`), rows at fixed spacing (main menu y =
index*15+95, right edge x 0x212; OPTIONS y = 90+i*10 at x 530). A bridge would turn hover into
Up/Down presses toward the hovered row (pad presses only, no writes to game memory), click = X,
right click = Triangle; for the rider carousel and the track map, left/right thirds of the picture =
Left/Right. That needs each menu's row geometry per shell menu id (`D_0029DED8`), and the race-start
state-trace check, since it reads game state.

Test desktops (DHD_TEST_INPUT, a desktop that is never shown): Windows reports a mouse leave after
each posted move there, and SDL then moves its pointer to the OS cursor and resyncs it there before
the next press. Only under DHD_TEST_INPUT, present.c takes the leave's motion back (learning the OS
cursor's point from it) and drops later motions to that point, so posted moves and clicks behave as
a real mouse's. Text typed by posted WM_CHAR does not arrive on such a desktop; the test entered the
join code with the letter picker (Left/Right) and mouse clicks.

### 1. Mouse on the game's own menus

The shell (`func_001EB4D0`, one screen per `D_0029DED8`) draws its lists with three text helpers
(`func_001F5398` left, `func_001F5D08` centred, `func_001F5EE8` right; styles `D_004C6560`, 0x58
bytes each, glyph sizes at +0x48). Two small patches report what it draws: `port_shell_frame()`
before the screen switch and `port_shell_text(align, style, x, y, text)` at the start of each
helper. Both only write host memory (menu_page.c keeps the last frame's texts). The menu structs are
static, one per screen (`func_001F7420`: first row +8, last +0xC, cursor +0x10, disabled flags
+0x1C); the table `shell_lists` in menu_page.c gives each list's address, first row's y and step
(main menu 15 / `D_004C6CA8` y 95; OPTIONS 2 / `D_004C6D98` y 90 step 10; controls 13; difficulty
19; players 10; multiplayer mode 24; new/continue 16 (y 85, or 95 with fewer rows); single-player
modes 1 (y 65); race type 11 (y 85, disabled rows not drawn and the rest packed, `func_001EF0E0`);
12, 17, 21, 22, 25, 30). A row is hit when the pointer is on what that frame drew at its y (measured
with the text's own style, `func_0020F860`), within half a step of the glyphs' middle.

The mouse acts by pad presses only, as on our pages (UI1), never by writing the game's cursors:
- lists: hover presses Up/Down toward the row, one at a time once the cursor has moved (given up
  after 32 presses, e.g. on a row the menu skips); a left click does the same and then Cross; a
  disabled row (POSTERS while locked) is not a target; the wheel is Up/Down;
- rider carousel (screens 3-6, `func_001F24B8`): a click on the left 35% is Left (previous rider),
  on the right 15% Right, in the middle (the rider) Cross; a click on the legend bar (bottom 14%)
  is the button it shows (PREV, NEXT, INFO = Square, SELECT, BACK); the wheel is Left/Right;
- title (0), the flight to the rider screen (32), RIDER SELECTED (33), the ride to the shop (34):
  a click is Cross;
- the shop (popup `D_003642D0`, vtable `D_00284190`): its list (BIKES / JERSEYS / BIKE COLOR) is a
  child menu at +0x500 (vtable `D_00287190`, rows at x 110, y 25, step 10; cursor -1 on the
  INVENTORY header). Its pictures refresh when that cursor moves by a press (`func_0013C128`),
  so hover drives it with Up/Down presses; a click on the focused row is Left left of its text,
  Right right of it, Cross on it; the wheel there is Left/Right (previous / next bike, jersey,
  colour); the legend (BACK, SELECT, START) is clickable;
- the track chooser (`D_004C7A30`, vtable `D_00288650`, a map rather than rows): a click on the
  left 35% is Left (previous track), on the right 35% Right, in the middle Cross; the legend
  (PREV, NEXT, SELECT, BACK) is clickable; the wheel is Left/Right;
- a right click is Triangle everywhere.
Nothing happens while riding (`D_0029E290`), without mouse use, or when no shell frame was drawn
in the last 8 fields. `DHD_MOUSE_TRACE=1` logs each screen (with what its frame drew), each popup
page (address, vtable, rows; the shop's list too) and each mouse action.

## Issue 18: online bike defaults

The room catches the shop on entry, before it writes the selected bike triple. The
rider screen retains SETUP+0x11C from the prior selection instead; EVENT_SETUP then
sends those three stale words. `func_001B99B8` copies them to the race slots and
`func_001FA7C0` derives a model from the first word. Pro riders need the complete
specific triple set by `func_001B7C08`, so mixing a pro rider with the stale stock
triple produces the wrong bike. The online AI and missing-ride fallback also used
the host's bike regardless of rider.

The port now sets a stock single-race fallback (17, 4, 0, also used by retail
`func_001B99B8`) for ordinary riders and asks `func_001B7C08` for each pro's
complete triple. It sends the result through the existing EVENT_SETUP; AI and
missing-player fallbacks use the same rider-based rule. Scripted races may select
pro riders for testing. This is a default, not a bike picker: reopening the retail
shop has the camera problem described above, and a new picker needs a reliable
mapping of available shop bikes and unlocks. The default is preferable to exposing
unverified part combinations.

Validation: `build_wasm.py` strict link and offset scan passed; `build_host64.py`
produced the Windows executable. In a 35-second minimized two-client race through
a local relay, scripted Eric Carter (rider 6) sent `29 6 5`, and the guest put
that same triple on his puppet; scripted Cosmo sent `17 4 0`, and the host put
that triple on his puppet. The regular AI slots used `17 4 0` on both clients.
Both game captures at GO+300 show the riders in the race, but the rear camera
angle does not establish the detailed appearance of each bike. The run was
intentionally stopped before race results; the interactive room and the other
pro riders were not exercised in this run.

Later check: online races with each of the five pros (E0, 100, 140, 180, 1A0); each puppet
carried its pro's own triple, and the regular riders 17 4 0.
